# MCP DriftGuard — canonical terminology glossary

This document is the project's **authoritative terminology register**. Product names are retained for readability, while definitions map them to established software engineering, security, cryptography and MCP terminology.

**Maintenance rule:** Every new user-facing technical term, claim, result field, interface, feature or renamed concept MUST be reviewed against this glossary in the same change that introduces it. Extend entries rather than creating conflicting definitions elsewhere. When terminology changes, update README, SPEC, THREAT_MODEL, skill instructions, CLI reporting and release notes together. Treat a missing or contradictory entry as a release-gate failure.

| Project term | Standard technical term | Precise interpretation / limitations |
| --- | --- | --- |
| MCP DriftGuard | MCP interface-configuration integrity verifier | Software comparing observations of an MCP endpoint with a separately approved reference |
| MCP surface | Externally observable MCP protocol interface | Advertised tools, resources, prompts, schemas, capabilities and selected protocol, auth and transport metadata |
| Inspect / observation | Protocol discovery / inventory collection | A snapshot of accessible declarations; no server-side MCP tool execution |
| Snapshot | Observed configuration-state record | Structured observation, with capture time as evidence metadata |
| Canonical snapshot | Canonically serialized configuration | Deterministic representation for stable comparisons |
| Fingerprint | SHA-256 cryptographic digest | Detects modification but does not independently establish provenance or approval |
| Baseline | Reference configuration / golden configuration | Saved reference artifact, only trusted after explicit approval |
| Candidate baseline | Proposed reference artifact | Generated by tooling; **not automatically approved** |
| Baseline approval | Change-control authorization | Human or independently authorized policy decision, separate from baseline creation |
| Signed baseline | Digitally signed reference artifact | Optional Ed25519 signature; depends on trusted public-key verification and key custody |
| Baseline tampering | Reference artifact integrity violation | Data changed in a way that fails canonical-hash or signature checks |
| Drift | Configuration deviation | Difference between a reference and observed externally visible state |
| Capability drift | API/feature inventory change | MCP tools, resources, prompts or capability declarations added, removed or altered |
| Authority drift | Potential privilege/operation scope change | Schema or declared behavior may broaden allowed inputs; not proof of backend privilege |
| Schema widening | Expansion of accepted input set | Risk classification based on recognized JSON Schema transformations |
| Description drift | Declared API metadata change | Changed textual descriptions; may indicate altered intent, not verified runtime behavior |
| Protocol drift | Protocol negotiation / advertised version change | Observed protocol compatibility metadata differs |
| Authorization drift | Authentication/authorization metadata change | Challenges, metadata locations, OAuth declarations or related observable state differ |
| Transport identity | TLS certificate / SPKI identity evidence | Cryptographic transport identifiers observed for the endpoint |
| TLS certificate rotation | X.509 certificate replacement | Certificate may change with or without underlying public-key change |
| PASS | No detected deviation under implemented checks | **Not** proof that server, baseline, binaries or backend are safe or unchanged |
| REVIEW | Detected lower-scored deviation | Review required; process exit code 1 |
| FAIL | Detected higher-scored deviation | Drift crossed implemented risk threshold; process exit code 2 |
| Probe failure | Incomplete or unsuccessful observation | Inconclusive verification; exit code 3, never PASS |
| Artifact failure | Reference/key file handling error | Baseline/key missing or unusable; exit code 4 |
| Integrity failure | Reference integrity or authenticity verification failure | Canonical hash/signature invalid; exit code 5 |
| Risk score | Rule-based severity aggregation | Deterministic heuristic, not probability of compromise |
| Fail-closed inventory | Reject incomplete discovery | Prevents partial inventory from being accepted as a complete observation |
| Legacy fallback | Version-negotiation compatibility path | Only on explicit supported evidence; not on generic auth or network errors |
| SSE | Server-Sent Events | HTTP event-stream response framing for MCP transport |
| Interoperability test | Cross-implementation compatibility test | Requires independent MCP server implementations and retained execution evidence |
| Agent skill | Portable procedural instructions (Agent Skills) | SKILL.md guides agents; not a separate security engine |
| OAuth issuer allowlist | Explicit origin-level authorization for external OAuth metadata discovery | Operator-controlled exact scheme-and-host approval; does not by itself authenticate the issuer or establish OAuth conformance |
| Stdio transport | MCP JSON-RPC over standard input/output | Local executable subprocess transport; executable launch itself is privileged even when tool discovery is read-only |
| Executable allowlist | Explicit application execution authorization | Operator-pinned absolute executable plus full ordered argument vector; not an OS sandbox or guarantee of binary content integrity |
| Conformance harness | Reproducible compatibility / negative-security test suite | Verifies stated scenarios and expected exit codes; does not establish formal certification |
| Agent adapter | Agent-specific integration layer | Minimal host-specific installation, tool invoking and packaging |
| Local-model test | Model-assisted integration test | Model explanations are untrusted/advisory; CLI results remain authoritative |
| Prompt injection | Instruction/data trust-boundary crossing | Malicious instructions embedded in discovered or retrieved MCP metadata |
| EDRG release gate | Evidence-driven release acceptance criterion | Project workflow: concrete checks and recorded evidence before promotion |
| Open core | Open-source functional implementation | Apache-2.0 local verifier remains independently useful |
| Professional service | Optional commercial managed functionality | Not part of core; unavailable until implemented, tested and separately licensed |
| SARIF | Static Analysis Results Interchange Format | Standard machine-readable report format for tooling |
| SPKI | SubjectPublicKeyInfo | Public-key material used for TLS identity fingerprinting |
| CI | Continuous integration | Automated checks for source changes |
| NOTICE | Attribution and legal notice file | Redistribute as required by the Apache-2.0 terms |

## Anti-confusion rules

- Do not equate **unchanged declared interface** with **unchanged implementation**.
- Do not equate **baseline creation** with **baseline approval**.
- Do not equate **cryptographic digest** with **trusted authenticity**.
- Do not equate **new tool discovered** with **tool invoked or data exfiltrated**.
- Do not equate **two SDK discovery passes** with **complete standards conformance**.
- Do not equate **skill metadata parsed** with **authenticated agent integration passed**.
- Do not call an optional, proposed or roadmap capability **implemented**.

## Change procedure

1. Identify terms touched by proposed code, UX, skill, reporting or documentation changes.
2. Update this register with the conventional technical equivalent and operational limitation.
3. Link from affected documents rather than copying a second, divergent canonical glossary.
4. Include a terminology-review note in the release evidence.
5. Execute the documentation consistency check and block publication on a failure.
